MeterFlow — System Design

1. Overview

MeterFlow is a usage metering and billing engine for SaaS applications.



The system tracks:



Tenants and their subscriptions

Available plans

Usage quotas defined by each plan

Usage events generated by tenants

Idempotent usage ingestion

Fast usage and rate-limit checks using Redis

Persistent business data using PostgreSQL through Supabase



The main design principle is:

PostgreSQL is the source of truth. Redis provides fast, temporary state.

9. Idempotency Strategy

Usage ingestion must be idempotent because duplicate requests must not result in duplicate billing or usage.



The client provides an idempotency_key with every usage request.



Example:

POST /usage

idempotency_key = req_abc123
quantity = 1


If the same request is sent again:

req_abc123


the service must recognize it as a duplicate.

Database Guarantee

idempotency_key should have a uniqueness constraint.



Conceptually:

USAGE_EVENTS
idempotency_key UNIQUE


This provides a durable database-level guarantee.

Without idempotency

Request 1 → +1 usage
Request 2 → +1 usage

Total = 2


With idempotency

Request 1 → +1 usage
Request 2 → duplicate

Total = 1


The uniqueness constraint makes the operation safe even if multiple requests arrive concurrently.

10. Redis Usage

Redis is not the source of truth for billing data.



PostgreSQL stores the durable records.



Redis is used for high-frequency state such as:



Rate limiting

Fast usage counters

Temporary quota state

Short-lived idempotency state where appropriate



Architecture:

                     ┌──────────────┐
                     │   FastAPI    │
                     └──────┬───────┘
                            │
                ┌───────────┴───────────┐
                │                       │
                ▼                       ▼
        ┌──────────────┐        ┌──────────────┐
        │    Redis     │        │  PostgreSQL  │
        │              │        │   Supabase   │
        ├──────────────┤        ├──────────────┤
        │ Rate limits  │        │ Tenants      │
        │ Counters     │        │ Plans        │
        │ Fast checks  │        │ Quotas       │
        │ Temporary    │        │ Subscriptions│
        │ state        │        │ Usage events │
        └──────────────┘        └──────────────┘


The guiding rule is:

Redis answers "what is the fast current state?" while PostgreSQL answers "what actually happened?"

11. Metering Flow

A typical usage request follows this flow:

sequenceDiagram

    participant Client
    participant API as FastAPI
    participant Redis
    participant DB as PostgreSQL

    Client->>API: POST /usage
    API->>DB: Get tenant subscription
    DB-->>API: Active plan

    API->>DB: Get quota
    DB-->>API: Quota limit

    API->>Redis: Check current usage
    Redis-->>API: Current counter

    alt Quota available
        API->>Redis: Increment counter
        API->>DB: Insert usage event
        DB-->>API: Event created
        API-->>Client: 201 Created
    else Quota exceeded
        API-->>Client: 429 Too Many Requests
    end


The implementation must ensure that Redis counters and durable usage records cannot silently create incorrect billing totals. PostgreSQL remains authoritative for reconciliation.

13. Design Principle

The system prioritizes correctness over simply maximizing performance.



In particular:



Money is stored using integer cents.

Usage events are persisted.

Idempotency keys prevent duplicate usage.

Quotas are associated with plans.

Subscriptions connect tenants to plans.

Redis is treated as a fast supporting layer rather than the billing source of truth.

PostgreSQL can be used to reconcile usage when necessary.
